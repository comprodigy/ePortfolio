Grand Strand Contact Service

CS 320 Software Testing, Automation, and QA. In-memory contact store with no UI. Enhanced for algorithms and data structures. Outcomes 3 and 4.

What it was

A contact has an ID, first name, last name, phone, and address, with length and format rules. ContactService supports add, update, delete, and lookup. JUnit covers the field rules and the service methods.

The original code already used a HashMap keyed by ID, so lookup by ID was already average O(1). IDs were random 10-letter strings created inside Contact. Uniqueness was only checked if the same object was added twice. updateContact skipped invalid fields instead of throwing. getContact returned null while delete and update threw. testAddContact never called addContact, and testGetContact still had a generated fail stub.

What changed

  • Named constants for field limits.
  • The service owns ID generation and retries while contacts.containsKey(id).
  • Contact takes the ID in the constructor and stores it as final. Still no ID setter.
  • updateContact calls the setters so bad data throws.
  • Missing IDs throw on get, update, and delete.
  • A second HashMap maps phone to ID for average O(1) lookup by phone. Extra memory, and both maps stay in sync. That trade-off is in the class comment.
  • Tests hit the service, including duplicate phone, invalid update, get-by-phone, and lookup after 200 contacts.

Narrative

I picked this artifact because it is small enough to show a structure choice and a trade-off without a UI in the way. CS 320 was also where I learned to prove behavior with JUnit. I did not need to swap a list for a map. I needed to make the algorithm around the map honest.

A good structure does not fix a bad uniqueness algorithm. The file already had a HashMap. The real issue was generating IDs in the model with no view of the collection. Moving that into the service and checking containsKey is the difference between “probably unique” and “unique in this store.” The second index made the trade-off concrete: one map is enough if you only look up by ID. Get-by-phone without scanning values costs another map and extra write work.

The tests were the annoying part. testAddContact never added a contact. Changing addContact to take fields meant rewriting tests. That was the right break. I would rather change the API than leave uniqueness inside Contact.
